# Feature Dictionary

## Phase 12 — Feature Engineering

This document is the single source of truth for the engineered features actually produced by the current Phase 12 Python pipeline in `src/data/feature_engineering.py`.

It covers only the four feature datasets that are currently generated by the implementation:

- `orders_features.csv` — one row per `order_id`
- `order_items_features.csv` — one row per `(order_id, order_item_id)`
- `customer_features.csv` — one row per `customer_unique_id`
- `monthly_features.csv` — one row per `year_month`

This dictionary intentionally excludes features that are not present in the current implementation. No speculative, unimplemented, or fabricated features are documented here.

---

## 1. Feature Dataset Overview

| Output Dataset | Grain | Purpose |
| --- | --- | --- |
| `orders_features.csv` | One row per `order_id` | Order-level time, seasonality, revenue, delivery, payment, and review features |
| `order_items_features.csv` | One row per `(order_id, order_item_id)` | Item-level revenue, freight, product weight, product volume, and item classification features |
| `customer_features.csv` | One row per `customer_unique_id` | Customer-level order counts, repeat purchase behaviour, lifetime revenue, and average order value |
| `monthly_features.csv` | One row per `year_month` | Monthly revenue and demand trends, rolling metrics, growth, and cumulative revenue |

---

## 2. Feature Engineering Principles

1. Features are created at explicitly defined grains and must not be merged into a dataset with a different grain unless the logic is intentionally designed to do so.
2. Aggregations occur before lower-grain data is joined into higher-grain datasets. For example, order-level revenue is aggregated from item-level data before being attached to `orders_features.csv`.
3. Revenue reconciliation is validated across feature outputs. The pipeline checks that order revenue sums reconcile to the item-level source and that customer lifetime revenue reconciles to the order-level totals.
4. Missing delivery timestamps produce `NaN` values in delivery metrics rather than artificial classifications. This avoids falsely labeling undelivered or incomplete orders as late or on time.
5. Feature logic must match the implementation pipeline exactly. The feature dictionary reflects the code, not a conceptual alternative design.
6. Division-by-zero conditions are handled explicitly. Where a denominator is zero or missing, the result is set to `NaN` instead of being calculated incorrectly.

---

## 3. Feature Naming Conventions

The pipeline uses predictable suffixes to keep feature semantics clear:

- `_days` — time-duration metrics, measured in days
- `_flag` — binary indicator features, usually 0/1, with `NaN` used where a meaningful classification does not exist
- `_count` — count-based outputs such as number of orders or order items
- `_revenue` — aggregated sales amount based on `price` at the relevant grain
- `_value` — monetary values that can include a combination of components, such as `price + freight_value`
- `_category` — categorical classifications derived from thresholds or quantiles
- `_ratio` — division-based metric, typically a ratio such as freight-to-price

---

## 4. Important Definitions

The following definitions are used consistently in the pipeline and must be treated as the project standard:

- `item_revenue` = item `price` only.
- `total_item_value` = `price + freight_value`.
- `order_revenue` = sum of `item_revenue` per `order_id`.
- `total_order_value` = sum of `total_item_value` per `order_id`.
- `delivery_difference_days` = actual customer delivery date minus estimated delivery date.
- Positive `delivery_difference_days` means late delivery.
- `repeat_customer_flag` = `customer_order_count > 1`.
- `review_score` aggregation uses the maximum available review score per `order_id`.
- `payment_value_per_order` is the sum of payment values for the order, not a replacement for `order_revenue`.

## 5. `orders_features.csv` — one row per `order_id`

**Source tables:** `orders_processed.csv`, `order_items_processed.csv`, `payments_processed.csv`, `reviews_processed.csv`  
**Output dataset / grain:** `orders_features.csv` / one row per `order_id`

| Feature | Output Dataset / Grain | Source Table(s) | Formula / Logic | Purpose |
| --- | --- | --- | --- | --- |
| `order_id` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Original `order_id` value from the source orders table | Unique order identifier |
| `customer_id` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Original `customer_id` carried through from the order record | Order-level customer linkage |
| `customer_unique_id` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv`, `customers_processed.csv` | Joined from `customer_id` to `customer_unique_id` using the customer lookup | Customer-level aggregation and segmentation |
| `order_status` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Original `order_status` value | Order-state analysis |
| `order_date` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `pd.to_datetime(order_purchase_timestamp).dt.date` and then back to datetime | Daily-order time indexing |
| `order_year` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Uses the existing `order_year` where present; otherwise fills from the purchase timestamp year | Annual reporting |
| `order_quarter` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Uses the existing `order_quarter` where present; otherwise calculates `(month - 1) // 3 + 1` from the purchase month | Quarterly seasonality analysis |
| `order_month_number` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Uses the existing `order_month` value if available; otherwise fills with the purchase timestamp month | Monthly grouping logic |
| `order_month_name` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Maps `order_month_number` to month names: January, February, March, April, May, June, July, August, September, October, November, December | Readable monthly reporting |
| `order_weekday` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `purchase_ts.dt.day_name()` | Weekly demand pattern analysis |
| `is_weekend` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `1` when `dayofweek >= 5`, otherwise `0` | Weekend demand flag |
| `year_month` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `purchase_ts.dt.to_period('M').astype(str)` | Monthly time-series key |
| `season` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Month-based season mapping: December/January/February = Summer; March/April/May = Autumn; June/July/August = Winter; September/October/November = Spring | Southern Hemisphere seasonal analysis |
| `holiday_season_flag` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `1` if `order_month_number` is `11` or `12`, otherwise `0` | Retail seasonality proxy for late-year demand |
| `quarter_seasonality` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | Maps `order_quarter` to `Q1`, `Q2`, `Q3`, `Q4` | Quarter-based comparison |
| `order_revenue` | `orders_features.csv` / one row per `order_id` | `order_items_processed.csv` | Sum of `item_revenue` by `order_id` where `item_revenue = price` | Gross order sales value excluding freight |
| `total_order_value` | `orders_features.csv` / one row per `order_id` | `order_items_processed.csv` | Sum of `total_item_value` by `order_id`, where `total_item_value = price + freight_value` | Total value including freight |
| `items_per_order` | `orders_features.csv` / one row per `order_id` | `order_items_processed.csv` | Count of `order_item_id` values per `order_id` | Order size and basket depth |
| `processing_time_days` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `(order_delivered_carrier_date - order_purchase_timestamp)` in days when both dates are valid; otherwise `NaN` | Shelf-to-carrier processing duration |
| `delivery_time_days` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `(order_delivered_customer_date - order_purchase_timestamp)` in days when both dates are valid; otherwise `NaN` | Total delivery duration |
| `estimated_delivery_time_days` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `(order_estimated_delivery_date - order_purchase_timestamp)` in days when both dates are valid; otherwise `NaN` | Promised delivery window |
| `delivery_difference_days` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `(order_delivered_customer_date - order_estimated_delivery_date)` in days when both dates are valid; otherwise `NaN` | Delivery timing relative to estimate |
| `late_delivery_flag` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `1` when the order is delivered and `delivery_difference_days > 0`; otherwise `NaN` because missing or incomplete deliveries are not classified | Late-delivery indicator |
| `on_time_delivery_flag` | `orders_features.csv` / one row per `order_id` | `orders_processed.csv` | `1` when the order is delivered and `delivery_difference_days <= 0`; otherwise `NaN` because missing or incomplete deliveries are not classified | On-time-delivery indicator |
| `number_payment_installments` | `orders_features.csv` / one row per `order_id` | `payments_processed.csv` | Maximum `payment_installments` per `order_id` | Installment intensity per order |
| `multi_payment_flag` | `orders_features.csv` / one row per `order_id` | `payments_processed.csv` | `1` if the order has more than one payment record (`payment_record_count > 1`), else `0` | Multi-payment usage flag |
| `payment_value_per_order` | `orders_features.csv` / one row per `order_id` | `payments_processed.csv` | Sum of `payment_value` grouped by `order_id` | Total cash collected per order |
| `review_score` | `orders_features.csv` / one row per `order_id` | `reviews_processed.csv` | Maximum `review_score` per `order_id` after grouping reviews to order grain | Deterministic order-level satisfaction score |
| `review_score_category` | `orders_features.csv` / one row per `order_id` | `reviews_processed.csv` | `Low` if `review_score <= 2`; `Neutral` if `review_score == 3`; `High` if `review_score >= 4` | Satisfaction segmentation |
| `low_review_flag` | `orders_features.csv` / one row per `order_id` | `reviews_processed.csv` | `1` when `review_score <= 2`, else `NaN` when no review exists | Low-satisfaction flag |
| `high_review_flag` | `orders_features.csv` / one row per `order_id` | `reviews_processed.csv` | `1` when `review_score >= 4`, else `NaN` when no review exists | High-satisfaction flag |

### Order feature rules

- `order_date` is the date portion of `order_purchase_timestamp`.
- `order_month_number` uses the processed source month if present; otherwise it is derived from the purchase timestamp month.
- `season` uses the following mapping, which matches the Southern Hemisphere calendar logic in the pipeline:
  - December, January, February = Summer
  - March, April, May = Autumn
  - June, July, August = Winter
  - September, October, November = Spring
- `holiday_season_flag` = `1` for months 11 and 12 only.
- `late_delivery_flag` and `on_time_delivery_flag` are not assigned values when an order has no valid actual delivery date or is not in delivered status; in those cases they remain `NaN`.

## 6. `order_items_features.csv` — one row per `(order_id, order_item_id)`

**Source tables:** `order_items_processed.csv`, `products_processed.csv`  
**Output dataset / grain:** `order_items_features.csv` / one row per `(order_id, order_item_id)`

| Feature | Output Dataset / Grain | Source Table(s) | Formula / Logic | Purpose |
| --- | --- | --- | --- | --- |
| `order_id` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | Original `order_id` | Item-to-order linkage |
| `order_item_id` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | Original `order_item_id` | Unique item identifier inside an order |
| `product_id` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | Original `product_id` | Product-level linkage |
| `seller_id` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | Original `seller_id` | Seller-level linkage |
| `item_revenue` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | `price` | Item-level sales value |
| `freight_value` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | Original `freight_value` | Shipping charge detail |
| `freight_to_price_ratio` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | `freight_value / price` when `price` is not missing and not zero; otherwise `NaN` | Shipping burden relative to price |
| `total_item_value` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `order_items_processed.csv` | `price + freight_value` | Total value of the item incl. shipping |
| `product_weight_g` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `products_processed.csv`, `order_items_processed.csv` | Product weight mapped onto the item row from the product dimension table | Product size and shipping analysis |
| `product_volume_cm3` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `products_processed.csv` | `product_length_cm × product_height_cm × product_width_cm` | Product volumetric size measure |
| `product_weight_category` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `products_processed.csv` | Weight bucket logic: `< 1000` = Light; `>= 1000 and < 5000` = Medium; `>= 5000 and < 20000` = Heavy; `>= 20000` = Very Heavy | Item weight segmentation |
| `product_dimension_category` | `order_items_features.csv` / one row per `(order_id, order_item_id)` | `products_processed.csv` | Classifies product volume using quantiles from valid volume values: `<= Q1` = Small; `> Q1 and <= Q2` = Medium; `> Q2 and <= Q3` = Large; `> Q3` = Extra Large | Product volume classification |

### Order item classification logic

- `product_weight_category` uses the exact thresholds implemented in the code:
  - Light: product weight < 1000
  - Medium: 1000 <= weight < 5000
  - Heavy: 5000 <= weight < 20000
  - Very Heavy: weight >= 20000
- `product_dimension_category` uses the product volume quartiles from valid values only. If no valid product volumes exist, the category column is set to `NaN`.
- `freight_to_price_ratio` is `NaN` when `price` is `NaN` or zero to avoid division-by-zero and invalid ratios.

## 7. `customer_features.csv` — one row per `customer_unique_id`

**Source tables:** `orders_processed.csv`, `orders_features.csv`  
**Output dataset / grain:** `customer_features.csv` / one row per `customer_unique_id`

| Feature | Output Dataset / Grain | Source Table(s) | Formula / Logic | Purpose |
| --- | --- | --- | --- | --- |
| `customer_unique_id` | `customer_features.csv` / one row per `customer_unique_id` | `orders_processed.csv` | Distinct customer identifier used for customer-level analysis | Customer identity |
| `customer_order_count` | `customer_features.csv` / one row per `customer_unique_id` | `orders_features.csv` | Count of distinct `order_id` values per `customer_unique_id` | Purchase frequency |
| `repeat_customer_flag` | `customer_features.csv` / one row per `customer_unique_id` | `customer_features.csv` | `1` when `customer_order_count > 1`, else `0` | Repeat-customer flag |
| `customer_lifetime_revenue` | `customer_features.csv` / one row per `customer_unique_id` | `orders_features.csv` | Sum of `order_revenue` across all orders belonging to the customer | Total customer revenue |
| `average_customer_order_value` | `customer_features.csv` / one row per `customer_unique_id` | `customer_features.csv` | `customer_lifetime_revenue / customer_order_count` when the count is greater than `0`; otherwise `NaN` | Average revenue per purchase |

### Customer aggregation rules

- Customer features use `customer_unique_id`, not `customer_id`.
- `customer_order_count` is the count of unique orders for that customer.
- `repeat_customer_flag` is defined exactly as `customer_order_count > 1`.

## 8. `monthly_features.csv` — one row per `year_month`

**Source tables:** `orders_features.csv`  
**Output dataset / grain:** `monthly_features.csv` / one row per `year_month`

| Feature | Output Dataset / Grain | Source Table(s) | Formula / Logic | Purpose |
| --- | --- | --- | --- | --- |
| `year_month` | `monthly_features.csv` / one row per `year_month` | `orders_features.csv` | Monthly period string derived from `order_date` using a monthly period index | Monthly time key |
| `monthly_revenue` | `monthly_features.csv` / one row per `year_month` | `orders_features.csv` | Sum of `order_revenue` by `year_month` | Monthly sales trend |
| `monthly_order_count` | `monthly_features.csv` / one row per `year_month` | `orders_features.csv` | Count of distinct `order_id` by `year_month` | Monthly demand volume |
| `3_month_rolling_revenue` | `monthly_features.csv` / one row per `year_month` | `monthly_features.csv` | Rolling sum over the current month and previous two months, using `rolling(window=3, min_periods=1).sum()` | Smoothed revenue trend |
| `3_month_rolling_order_count` | `monthly_features.csv` / one row per `year_month` | `monthly_features.csv` | Rolling sum over the current month and previous two months for order count | Smoothed demand trend |
| `monthly_revenue_growth` | `monthly_features.csv` / one row per `year_month` | `monthly_features.csv` | `(current_month_revenue - previous_month_revenue) / previous_month_revenue` when the previous month exists and is non-zero; otherwise `NaN` | Month-over-month revenue change |
| `cumulative_revenue` | `monthly_features.csv` / one row per `year_month` | `monthly_features.csv` | Running cumulative sum of `monthly_revenue` | Long-run revenue accumulation |

### Monthly feature rules

- The monthly dataset is sorted by `year_month` before rolling operations.
- `monthly_revenue_growth` is set to `NaN` when there is no prior month or when the previous month revenue is zero.
- `cumulative_revenue` is the cumulative sum of `monthly_revenue` across the ordered monthly series.
